# Deployment: Render + Supabase + GitHub Actions

This is how the public demo runs. Every piece is on a free plan.

```
GitHub repo ──push──▶ Render web service (gunicorn, Flask)  ──SQL──▶ Supabase PostgreSQL
     │                                                                   ▲
     └── Actions: tests on every push (SQLite + PostgreSQL)              │
         Actions: nightly "demo-reset" rebuilds the demo data ───────────┘
```

| Piece | Why | Free-plan limits that matter |
|---|---|---|
| **Supabase** | Managed PostgreSQL 15+ | 500 MB (the demo uses ~35 MB). Projects **pause after 7 days without activity**, but the nightly job counts as activity |
| **Render** | Runs the Flask app with gunicorn | 512 MB RAM (the app uses ~150 MB), sleeps after 15 min idle (~1 min cold start), disk wiped on restart. Generated PDFs and the model summary are therefore also stored in the database (`stored_files`) |
| **GitHub Actions** | CI, and the nightly demo rebuild | Scheduled workflows are paused by GitHub after 60 days without commits to a public repo. GitHub emails first; re-enable with one click |

## 1. Supabase (database)

1. Create a project. Choose region **Central EU (Frankfurt)** to sit next to Render's Frankfurt region, and save the database password it generates.
2. **Connect** → **Session pooler** → copy the URI. It looks like
   `postgresql://postgres.<project-ref>:<password>@aws-0-eu-central-1.pooler.supabase.com:5432/postgres`.
   Use the *pooler* URI: Supabase's direct host is IPv6-only, and Render connects over IPv4.
3. No SQL to run by hand. The app creates its tables on first start (`schema_postgres.sql`), and `demo` fills them.

## 2. GitHub (code, CI, nightly data)

1. Repository **Settings → Secrets and variables → Actions**:
   - Secret `SUPABASE_DB_URL` = the pooler URI from step 1.
   - Variable `DEMO_SITE_URL` = the Render URL (after step 3; optional, it wakes the site after each rebuild).
2. **Actions → demo-reset → Run workflow** loads the demo data (about 2–4 minutes). After that it runs every night at 03:00 Riyadh.

`demo-reset` generates 12 full months ending last month, so the demo never looks stale.

## 3. Render (web app)

**New → Blueprint** → pick this repository. `render.yaml` defines everything:

| Setting | Value |
|---|---|
| Build | `pip install -r requirements.txt` |
| Start | `gunicorn --workers 1 --threads 4 --timeout 120 --bind 0.0.0.0:$PORT "hr_analytics.web:create_app()"` |
| Health check | `/healthz` (checks the database too) |
| `HR_DATABASE_URL` | the Supabase pooler URI (Render asks for it; it is never committed) |
| `HR_SECRET_KEY` | generated by Render |
| `HR_DEMO_MODE=1` | one-click role buttons; showcase accounts cannot be locked or changed by visitors |
| `HR_BEHIND_PROXY=1`, `HR_SESSION_COOKIE_SECURE=1`, `TZ=Asia/Riyadh` | correct client IPs, HTTPS-only cookies, local time |

Every push to `main` redeploys automatically.

## Security notes for a real deployment

- **Never set `HR_DEMO_MODE` on a database with real people in it.** The role buttons skip passwords. As a safety net they also refuse any employee not flagged `is_synthetic`.
- Create real accounts with `python -m hr_analytics create-user` or from **User accounts**. Temporary passwords must be changed at first sign-in.
- The login throttle is kept in memory per process. With several instances, use a shared store (see `production_migration.md`).
- Back up Supabase: free projects have no point-in-time recovery. Use `pg_dump` against the pooler URI.

## Running the PostgreSQL build locally

```bash
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=pg postgres:16
export HR_DATABASE_URL=postgresql://postgres:pg@localhost:5432/postgres
python -m hr_analytics demo && python -m hr_analytics.web
HR_TEST_DATABASE_URL=$HR_DATABASE_URL python -m unittest discover -s tests -t .   # each test uses its own schema
```
