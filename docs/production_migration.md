# الانتقال إلى بيئة الإنتاج

النسخة الحالية مصممة للتشغيل المحلي والعرض والتجربة. هذا الملف يحدد ما يجب تغييره قبل استخدامها مع بيانات حقيقية.

## 1. قاعدة البيانات: من SQLite إلى PostgreSQL أو SQL Server

### ما هو جاهز للنقل

- المخطط في `hr_analytics/db/schema.sql` مكتوب بـ SQL قياسي قدر الإمكان.
- معظم الاستعلامات في `hr_analytics/db/repos.py`، وتستخدم معاملات `?` بدل دمج النصوص.
- قواعد الصلاحيات (`security/scope.py`) تبني شروط WHERE بمعاملات، فلا تعتمد على محرك بعينه.

### ما يجب تعديله

| المسألة | SQLite الآن | PostgreSQL | SQL Server |
|---|---|---|---|
| المفتاح الأساسي التلقائي | `INTEGER PRIMARY KEY` | `GENERATED ALWAYS AS IDENTITY` | `IDENTITY(1,1)` |
| رمز المعاملات | `?` | `%s` مع psycopg | `?` مع pyodbc |
| رقم الصف المُدرج | `cursor.lastrowid` | `RETURNING id` | `OUTPUT INSERTED.id` |
| عدد الصفوف المدرجة فعلًا | `conn.total_changes` | `cursor.rowcount` | `@@ROWCOUNT` |
| `ON CONFLICT ... DO NOTHING / DO UPDATE` | مدعوم | مدعوم | `MERGE` |
| الفهارس الجزئية `WHERE status IN (...)` | مدعومة | مدعومة | Filtered index |
| `substr(shift_date, 1, 7)` | نص | `to_char(shift_date, 'YYYY-MM')` | `FORMAT(shift_date, 'yyyy-MM')` |
| `datetime('now')` افتراضيًا | في schema.sql | `now()` | `SYSDATETIME()` |
| التواريخ | TEXT بصيغة ISO | `DATE` / `TIMESTAMP` | `DATE` / `DATETIME2` |
| `INSERT OR IGNORE` | سطر واحد في schema.sql | `ON CONFLICT DO NOTHING` | `IF NOT EXISTS` |
| `PRAGMA foreign_keys / journal_mode` | في connection.py | يُحذف | يُحذف |
| `executescript` | في connection.py | ملف ترحيل (Alembic أو Flyway) | نفس الشيء |
| ترقية المخطط v1 → v2 (`migrate()`) | `PRAGMA table_info` وإعادة بناء `leave_requests` لأن SQLite لا تعدّل قيد CHECK | `ALTER TABLE ... DROP/ADD CONSTRAINT` في ملف ترحيل | نفس الشيء |

### أماكن SQL خارج `repos.py`

هذه قائمة مراجعة كاملة وقت كتابة هذا الملف (عدد الاستدعاءات بين قوسين). ميزات v2 (الطلبات، والموافقات، ولوحة Today، والحسابات، والاستيراد الجماعي) وضعت كل استعلاماتها في `repos.py`، ما عدا ترقية المخطط في `db/connection.py`:

| الملف | الاستدعاءات | ما يحتويه |
|---|---|---|
| `security/scope.py` | 5 | تحميل المستخدم، والتحقق من الموظف |
| `reports/runner.py` | 6 | سجل تشغيل التقارير |
| `services/seed.py` | 11 | تحميل البيانات الاصطناعية وطلبات العرض التجريبية؛ لا يُستخدم في الإنتاج |
| `exports/powerbi.py` | 8 | قراءة الجداول للتصدير |
| `cli.py` | 4 | |
| `web/views/admin.py` | 4 | مزامنة أدوار المديرين، وقائمة المرشحين |
| `reports/monthly.py` | 2 | |
| `ml/risk_model.py` | 2 | |
| `pipeline/processor.py` | 1 | فحص بصمات اليوم السابق |

الخطوة الأنسب: نقل هذه الاستعلامات إلى `repos.py` ضمن الترحيل نفسه، ثم استبدال طبقة الاتصال بـ SQLAlchemy Core أو بمحوّل خاص بالمحرك.

### ترحيل البيانات

1. أنشئ المخطط في المحرك الجديد.
2. انقل الجداول بالترتيب: departments، shifts، employees، ثم باقي الجداول، مع الحفاظ على قيم المفاتيح.
3. اضبط تسلسل المفاتيح التلقائية بعد النقل.
4. أعد تشغيل `process` لآخر شهرين.
5. قارن `validation/expected_kpis.csv` قبل الترحيل وبعده.

## 2. تشغيل التطبيق

- **خادم التطوير:** `python -m hr_analytics.web` للاستخدام المحلي فقط.
- **الإنتاج:** خادم WSGI خلف HTTPS:
  - Linux: `gunicorn -w 4 "hr_analytics.web:create_app()"`.
  - Windows: `waitress-serve --call hr_analytics.web:create_app`.
  - هذان الخادمان **لم يُثبَّتا أو يُختبرا** في بيئة البناء، وعليك إضافتهما للمتطلبات مع رقم الإصدار.
- **HTTPS:** إلزامي عبر Nginx أو IIS أو موازن الأحمال. بعده اضبط `HR_SESSION_COOKIE_SECURE=1`.
- **الأسرار:**
  - `HR_SECRET_KEY` من خزنة أسرار أو متغيرات بيئة الخادم، وليس من ملف في المستودع.
  - تغيير المفتاح يُخرج كل المستخدمين، وهذا متوقع.

## 3. الأمان

| البند | الحالي | المطلوب للإنتاج |
|---|---|---|
| الدخول | اسم مستخدم وكلمة مرور مشفّرة (scrypt) | SSO عبر Microsoft Entra ID (OIDC)، بنفس البريد المستخدم في RLS |
| حد المحاولات | في ذاكرة العملية | مخزن مشترك (Redis أو جدول) مع عدة عمليات |
| CSRF | رمز لكل جلسة، مفحوص في `before_request` | كافٍ؛ أو Flask-WTF إذا فُضّل مكوّن جاهز |
| الترويسات | CSP صارمة، `nosniff`، `DENY`، و`no-store` للصفحات المحمية | إضافة `Strict-Transport-Security` عند HTTPS |
| سجل التدقيق | الدخول، والاستيراد، والمعالجة، والتقييمات، والتصدير، والتقارير، وتعديلات البيانات الأساسية | نقله أو نسخه لمخزن لا يعدّله مستخدمو التطبيق |
| رفض الوصول | يُسجَّل في log التطبيق | توجيه السجلات إلى نظام مراقبة |
| إدارة الحسابات | أمر `create-user` | شاشة HR لإدارة الحسابات، أو الاعتماد الكامل على SSO |

## 4. البيانات الشخصية والاحتفاظ

- بيانات الحضور والتقييم بيانات شخصية. ضع سياسة احتفاظ تحدد:
  - مدة حفظ البصمات الخام.
  - مدة حفظ نسخ الملفات في `instance/uploads`.
  - مدة حفظ ملفات PDF.
- راجع المتطلبات مع جهة الحوكمة القانونية وفق نظام حماية البيانات الشخصية في المملكة.
- **النسخ الاحتياطي:**
  - نسخ يومي لقاعدة البيانات ومجلد `instance/uploads` و`output/reports`.
  - اختبار الاستعادة دوريًا.
  - SQLite في وضع WAL: انسخها بـ `sqlite3 .backup` أو أوقف التطبيق قبل النسخ.

## 5. التعرف على الوجه (OpenCV / DeepFace): مؤجل عمدًا

الطلب ذكره كامتداد اختياري، وقد أُجّل للأسباب التالية:

- **حساسية البيانات:** صور الوجه وقوالبها بيانات حيوية حساسة، وتحتاج أساسًا نظاميًا وموافقة وضوابط تخزين وحذف أشد بكثير من البصمات الحالية.
- **مخاطر الدقة والعدالة:** دقة التعرف تختلف بين الفئات والإضاءة والكاميرات. خطأ في المطابقة يعني غيابًا أو تأخرًا مسجلًا على شخص بريء.
- **لا حاجة لها في المسار الحالي:** أجهزة الحضور تنتج البصمات أصلًا، والنظام يستقبلها بشكل مستقل عن طريقة التقاطها.

**إذا تقرر تنفيذها لاحقًا**، تكون خدمة منفصلة:
- تُخرج بصمات بنفس صيغة الملفات الحالية (`badge_id`، `punch_time`، `device_id`)، فلا يتغير شيء في النظام.
- لا تخزن الصور بعد المطابقة.
- تتضمن مسار تصحيح يدوي وتقييم دقة موثّق قبل التشغيل.

## 6. Power BI

- استبدل مصدر CSV بالاتصال المباشر بقاعدة الإنتاج، عبر views تحمل نفس أسماء الأعمدة.
- المقاييس وأدوار RLS لا تتغير.
- DirectQuery يصبح ممكنًا بعد مغادرة SQLite، لكن Import مع تحديث مجدول يكفي عادة لبيانات يومية.
